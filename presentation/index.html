Chapitre 2 · Le concept

Le back en YAML : les labels font le lien

kind: Deployment
metadata: {name: back}
spec:
  replicas: 2
  selector:
    matchLabels: {app: back}
  template:
    metadata:
      labels: {app: back}
    spec:
      containers:
      - name: back
        image: …/croustino-back:1.0
        envFrom:
        - configMapRef: {name: back-config}

kind: Service
metadata: {name: back}
spec:
  selector: {app: back}
  ports:
  - port: 8080
    targetPort: http

kind: ConfigMap
metadata: {name: back-config}
data:
  DB_HOST: postgres
  STOCK_MAX: "24"

Le selector du Deployment doit correspondre aux labels du template. Le Service utilise les mêmes labels. DB_HOST vaut « postgres » : c'est le nom du Service de la base, résolu par le DNS du cluster.

Chapitre 3 · La solution

Les données vivent hors du pod, sur un volume qui lui survit

AVANT

Pod supprimé = données supprimées

APRÈS

postgres-0

PVC

disque

Le nouveau postgres-0 retrouve le même volume

Deux briques : une StorageClass qui crée les volumes à la demande, un StatefulSet qui donne à chaque pod une identité et son volume.

Le pod garde le même nom et le même PVC : c'est ce qui rend la migration vers Helm possible au chapitre 6 sans perdre les commandes.

Chapitre 3 · Le concept

Le provisionnement dynamique

POD

« je monte le volume data »

PVC · la demande

« 1 Gi, en RWO »

PV · le volume réel

un dossier sur worker1

Personne ne crée le PV à la main : la StorageClass le fabrique quand un PVC le demande.

WaitForFirstConsumer : le volume n'est créé qu'une fois le pod placé, sur le nœud du pod.

reclaimPolicy: Delete : supprimer le PVC efface les données.

kind: StorageClass
metadata:
  name: local-path
  annotations:
    # StorageClass par défaut
    storageclass.kubernetes.io/
      is-default-class: "true"
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer

local-path est parfait pour la formation mais lie le volume à un nœud. En production : un stockage réseau ou distribué (Longhorn, Ceph, CSI du cloud). On le reverra au chapitre 11 pendant le drain des nœuds.

Chapitre 3 · Le concept

PVC et PV en YAML

1. Le PVC : ce qu'on écrit

apiVersion: v1
kind: PersistentVolumeClaim

  name: test-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 100Mi
# pas de storageClassName :
# la classe par défaut

2. Le pod qui l'utilise

kind: Pod
metadata: {name: conso}
spec:
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: test-pvc
  containers:
  - name: conso
    image: busybox
    volumeMounts:
    - name: data
      mountPath: /data

3. Le PV : créé tout seul

kind: PersistentVolume
metadata:
  name: pvc-3f2a…
spec:
  capacity:
    storage: 100Mi
  accessModes:
  - ReadWriteOnce
  claimRef:
    name: test-pvc
  storageClassName: local-path
  hostPath:
    path: /opt/local-path-…

accessModes : ReadWriteOnce (un nœud), ReadOnlyMany, ReadWriteMany (plusieurs nœuds, stockage réseau).

On n'écrit que le PVC et le pod. Le PV est visible avec kubectl get pv -o yaml : il est lié au PVC par claimRef. Le volume du pod (data) fait le lien entre volumeMounts et le PVC. Le pod du TP est lancé avec kubectl run --overrides, qui contient exactement ce YAML en JSON.

Chapitre 5 · L'incident

« Le service promos a mangé toute la RAM »

7h02

Un prestataire a déployé le service « promos » dans croustino. Copié d'un traitement big data, chaque pod réserve et consomme presque toute la mémoire d'un worker. Les pods de Croustino, qui ne déclarent rien, sont sacrifiés : back et PostgreSQL évincés en plein rush.

Chapitre 5 · La solution

Des limites à trois niveaux

NŒUD · allocatable : ce que le scheduler peut distribuer

NAMESPACE croustino · LimitRange (valeurs par défaut, maximum) + ResourceQuota (plafond total)

back

req 100m / 128Mi

lim 500m / 256Mi

postgres

req 500m / 512Mi

lim 500m / 512Mi

promos

demande 7 Gi

→ refusé (max 1Gi)

CONTENEUR · requests (réservé) et limits (plafond)

Avec le LimitRange, promos est refusé dès la création : aucun conteneur ne peut dépasser 1Gi. En déclarant leurs ressources, back et PostgreSQL deviennent Burstable et Guaranteed : ils ne sont plus les premiers sacrifiés. Le quota empêche une équipe de réserver tout le cluster, même avec des pods raisonnables.

Chapitre 5 · Le concept

Requests pour placer, limits pour protéger

Mémoire allocatable de worker1 (3,5 Gi) : le scheduler additionne les requests

postgres

back

système

libre pour de nouveaux pods

Dépasser sa limite CPU

Le conteneur est ralenti (throttling). Il survit.

Dépasser sa limite mémoire

Le conteneur est tué : OOMKilled.

Classe QoSQuandÉvincé
BestEffortrien de déclaréen premier
Burstablerequests < limitsensuite
Guaranteedrequests = limitsen dernier

PostgreSQL passe en Guaranteed : c'est lui qu'on protège.

Le scheduler ne regarde jamais la consommation réelle, seulement les requests. Un pod sans requests peut atterrir sur un nœud déjà plein. kubectl top (metrics-server) montre la consommation réelle, utile pour choisir les valeurs.

Chapitre 5 · Le concept

LimitRange et ResourceQuota

LimitRange : règles par conteneur

kind: LimitRange
metadata:
  name: defauts-conteneurs
  namespace: croustino
spec:
  limits:
  - type: Container
    defaultRequest: {cpu: 100m, memory: 128Mi}
    default: {cpu: 500m, memory: 256Mi}
    max: {cpu: "1", memory: 1Gi}

ResourceQuota : plafond du namespace

kind: ResourceQuota
metadata:
  name: plafond-croustino
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.memory: 4Gi
    pods: "15"

$ kubectl scale deploy front --replicas=20
Error creating: pods "front-…" is forbidden: exceeded quota: plafond-croustino

Piège classique : dès qu'un quota CPU/mémoire existe, tout pod doit déclarer ses requests et limits, sinon il est refusé. Le LimitRange fournit les valeurs par défaut. Il ne s'applique qu'aux pods créés après lui : rollout restart.

Chapitre 8 · Le concept

Le chemin d'une ligne de log

CHAQUE NŒUD

pod back

écrit sur stdout

/var/log/
containers/

Fluent Bit · DaemonSet

lit les fichiers, ajoute pod, namespace, labels

Elasticsearch

un index par jour

kube-2026.10.09

Kibana

recherche, filtres, visualisations

Pourquoi un DaemonSet ?

Un collecteur par nœud lit les fichiers locaux. Un nœud ajouté = un collecteur de plus, automatiquement.

Pourquoi un opérateur (ECK) ?

Elasticsearch a besoin de certificats, de mots de passe, de volumes : l'opérateur gère tout ça.

ECK crée le Secret logs-es-elastic-user (mot de passe), les certificats TLS et le PVC. Elasticsearch demande 2 Go : vérifier kubectl top nodes avant l'installation.

Chapitre 8 · Le concept

Logs JSON : une info, un champ

Ce que le back écrit sur stdout :

{"niveau": "ERROR", "evenement": "commande_rejetee", "commande_id": "1268863b",
 "client": "Mme Lebrun", "quantite": 30, "raison": "fournée insuffisante (max 24)"}

Ce que Fluent Bit ajoute :

"kubernetes": {
  "namespace_name": "croustino",
  "pod_name": "back-7d9f-x2k",
  "node": "worker2" … }

Ce qu'on tape dans Kibana (KQL) :

kubernetes.namespace_name : "croustino"
and client : "Mme Lebrun"
and niveau : "ERROR"

Réponse en 2 secondes : commande 1268863b, 30 croissants, rejetée car la fournée est limitée à 24. Le pod n'existe plus, la trace oui.

Avec du texte libre, il faudrait des expressions régulières fragiles. En JSON, le filtre kubernetes de Fluent Bit (Merge_Log On) transforme chaque clé en champ interrogeable.

Chapitre 9 · Le concept

Une politique : la première règle gagne

None

rien : les sondes, les events, le bruit

Metadata

qui, quoi, quand, sans le contenu

Request

+ le corps de la requête

RequestResponse

+ la réponse : tout, mais volumineux

Les Secrets : jamais au-delà de Metadata, sinon les mots de passe finissent dans le journal.

apiVersion: audit.k8s.io/v1
kind: Policy
rules:
# 1. le bruit
- level: None
  resources: [{resources: [events]}]
# 2. secrets : qui, jamais quoi
- level: Metadata
  resources: [{resources: [secrets]}]
# 3. les lectures
- level: None
  verbs: [get, list, watch]
# 4. modifs dans croustino
- level: RequestResponse
  namespaces: [croustino]
- level: Metadata

L'ordre compte : la règle des Secrets est avant celle des lectures, sinon la lecture d'un Secret ne serait jamais tracée. La politique complète est dans k8s/audit/audit-policy.yaml.

Chapitre 9 · Le concept

Mener l'enquête avec jq

Topologie « etcd empilé » (stacked) : etcd sur les control planes, la plus simple. Topologie « etcd externe » : etcd sur ses propres machines, plus robuste mais plus de VM. Best practices : nombre impair de membres etcd, sauvegardes externalisées, nœuds répartis sur plusieurs zones.

Chapitre 11 · Le concept

Sauvegarder et restaurer etcd

snapshot save

photo de tout le cluster

l'accident

namespace supprimé

snapshot restore

dans un nouveau dossier

échange

les données restaurées remplacent les anciennes

# sauvegarde (etcdctl est dans le pod etcd)
kubectl -n kube-system exec etcd-controlplane -- etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=…/server.crt --key=…/server.key \
  snapshot save /var/lib/etcd/sauvegarde-tp11.db
# restauration dans un nouveau dossier
kubectl -n kube-system exec etcd-controlplane -- etcdutl snapshot restore \
  /var/lib/etcd/sauvegarde-tp11.db --data-dir /var/lib/etcd/restauration …
# puis : etcd arrêté, /var/lib/etcd remplacé par la restauration, etcd relancé

Une restauration ramène tout le cluster en arrière : à réserver aux catastrophes. Pour un namespace, on redéploie depuis Git et Helm.

Ne pas faire pointer etcd.yaml vers le dossier restauré : kubeadm régénère ce manifest à la mise à jour, depuis sa propre configuration, et etcd repartirait sur les anciennes données. On remet donc les données restaurées à l'emplacement standard. La sauvegarde doit partir hors du control plane (stockage objet, autre site) et être testée. Velero est l'outil de référence pour sauvegarder des namespaces et leurs volumes.

drain évince les pods du nœud. Le PodDisruptionBudget interdit d'en retirer trop à la fois.

Une mineure à la fois : 1.34 → 1.35 → 1.36. Jamais de saut.

Piège : postgres-0 est lié à son disque local. Pendant le drain de son nœud, il attend.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: back
spec:
  maxUnavailable: 1
  selector:
    matchLabels: {app: back}

Pendant tout le TP, une boucle curl surveille le site : les participants voient en direct ce que protège le PDB, et ce qui casse quand le nœud de PostgreSQL est drainé. Excellente discussion pour la question des single points of failure.
