Chapitre 3 · Le concept

PVC et PV en YAML

1. Le PVC : ce qu'on écrit

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: test-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 100Mi
# pas de storageClassName :
# la classe par défaut

2. Le pod qui l'utilise

kind: Pod
metadata: {name: conso}
spec:
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: test-pvc
  containers:
  - name: conso
    image: busybox
    volumeMounts:
    - name: data
      mountPath: /data

3. Le PV : créé tout seul

kind: PersistentVolume
metadata:
  name: pvc-3f2a…
spec:
  capacity:
    storage: 100Mi
  accessModes:
  - ReadWriteOnce
  claimRef:
    name: test-pvc
  storageClassName: local-path
  hostPath:
    path: /opt/local-path-…

accessModes : ReadWriteOnce (un nœud), ReadOnlyMany, ReadWriteMany (plusieurs nœuds, stockage réseau).

On n'écrit que le PVC et le pod. Le PV est visible avec kubectl get pv -o yaml : il est lié au PVC par claimRef. Le volume du pod (data) fait le lien entre volumeMounts et le PVC. Le pod du TP est lancé avec kubectl run --overrides, qui contient exactement ce YAML en JSON.
